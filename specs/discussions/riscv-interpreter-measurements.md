# Measurements: RISC-V code generation as seen by an interpreter

> Raw data behind `interpreter-targeted-codegen.md`, plus the instruction fusion work that prompted
> the investigation. Kept separate because the handoff should not be about fusion; this is where the
> numbers, the tooling and the traps live.

## 1. What was being measured

The interpreter in `crates/execution/ab-riscv-interpreter`, running:

- **Two cryptographic workloads** — BLAKE3 chunk hashing and ed25519 verification, compiled from
  Rust to a contract with
  `crates/contracts/core/ab-contracts-tooling/src/riscv64-unknown-none-abundance.json`. Small, hot,
  arithmetic-heavy.
- **CoreMark**, compiled from C by whichever toolchain `RISCV_CC` names. Ordinary integer and
  pointer code, and the only workload here whose compiler can be swapped.

Guest ISA: RV64 with `m`, `b` (Zba+Zbb+Zbs), `zbc`, `zca`, `zcb`, `zcmp`, `zicond`, `zkn`, unaligned
scalar memory. No F/D, no V.

Two dispatch strategies: a `match` loop, and threaded dispatch via `explicit_tail_calls` with one
handler per instruction variant. Threaded is roughly 8× faster and is the one that matters. Two
fetchers: lazy (decode on the fly) and eager (decode the whole program into fixed-size slots up
front). Eager plus threaded is the configuration being optimized.

**Measurement host: a 4-core Intel Xeon @ 2.1 GHz VM, where the run-to-run spread on identical
binaries is about ±5%.** Wall-clock numbers will not reproduce elsewhere; dispatch counts will.

## 2. Instruction fusion in the interpreter

### 2.1 What it is here

A pass over the decoded stream replaces an adjacent pair with one instruction of twice the size, so
the fetcher steps over both and the pair costs one dispatch. The second instruction keeps its own
slot, so a branch into the middle of a fused pair still executes it on its own.

The rule: the first instruction's destination register is also the second's source and destination,
and is not the zero register. That makes the intermediate value dead and the fused instruction
exactly equivalent to the pair. It is the same condition LLVM's `SimpleFusion` imposes, via
`TieReg<0,1>`, `SecondInstHasSameReg<0,1>` and `OneUse`, so nothing is lost to being stricter than
LLVM. A fusion reading a third register must additionally require that register not to be the
destination, or it would read a value that no longer exists.

### 2.2 What it is worth

Counted with `cargo run --release -p ab-riscv-benchmarks --example dispatch_count`:

| | LLVM's fusion list only | plus three pairs found in the code |
|---|---|---|
| fusable pairs, of 198 with a dead intermediate | 43 | 155 |
| hashing, dispatches saved | 1 / 14583 (0.007%) | 497 / 14583 (3.41%) |
| signature verify, dispatches saved | 6325 / 654763 (0.97%) | 8519 / 654763 (1.30%) |

The three added pairs — `addi`+`sh3add` (43 occurrences), `addi`+`addi` (38), `xor`+`roriw` (31) —
are none of them an LLVM macro fusion. They are simply what the code contains: indexing a field of
an array of structures, and the core of every ARX construction.

CoreMark shows the same thing from the compiler's side:

| build | static instructions | fusable pairs | dispatches removed by fusion |
|---|---|---|---|
| GCC 14.2 | 8387 | 30 (0.36%) | 1.22% |
| LLVM, `generic-rv64` | 5070 | 78 (1.54%) | 0.48% |
| LLVM, `generic-interpreter-rv64` | 6703 | 219 (3.27%) | **8.29%** |

**What fusion is worth is decided almost entirely by which pairs the compiler emitted**, not by the
fusion rules. That is what turned the investigation towards code generation.

### 2.3 Verdict

Only when the compiler cooperates — and §5.6 later showed that when it does not, running the fusion
pass is a **net loss** in wall clock, not merely a small win: −3.7% on GCC's binary and −4.9% on
`generic-rv64`'s, against +9.7% on interpreter-targeted code. Its per-instruction overhead is paid
on every dispatch and the saving is not. See `interpreter-targeted-codegen.md` §5.5 and §5.6 below
for how code generation turns it from a liability into the single largest win available.

## 3. LLVM's fusion tune features

LLVM has 20 RISC-V fusion features. Nineteen are named `fusion-<name>`, generated by the
`Fusion` TableGen class in `llvm/include/llvm/Target/TargetMacroFusion.td` as
`SubtargetFeature<"fusion-" # name, ...>`. The twentieth, `conditional-cmv-fusion`, is a plain
`SubtargetFeature` in `RISCVFeatures.td` and does not follow the pattern. **Older LLVM spelled them
`<name>-fusion`**, so a list copied from anywhere else is likely to be silently ignored.

Turning them on changes what LLVM emits. Counting adjacent pairs by the interpreter's rule on a Rust
CoreMark port:

| configuration | fusable pairs |
|---|---|
| no fusion features | 1993 |
| the twelve long-standing ones | 2925 (+932) |
| all eighteen `fusion-*` | 2952 (+27 more) |

Individually, of the six newest: `fusion-shift-bit-extract` +61, `fusion-logic-reg-reg` +22,
`fusion-mul-add` +8, `fusion-logic-reg-imm` +7, `fusion-logic-imm-reg` 0, `fusion-add-mem` −33. The
last two earn nothing measurable.

On CoreMark built through LLVM, the fusion features take fusable pairs from 70 to 153.

`conditional-cmv-fusion` is roughly a wash for an interpreter, and cuts both ways: in one function it
turns a branchless `czero.nez`/`czero.eqz`/`or` sequence into `bltz`+`mv`, and in another it turns
`seqz`/…/`or` into `addi`/`czero.nez`, one dispatch fewer.

## 3.5 Does a newer GCC help?

No. Asked because GCC 16.1.0 from a riscv-gnu-toolchain nightly is two years newer than 14.2, and
CRC-identical output confirms both are correct builds:

| toolchain | static instructions | dispatches, unfused | dispatches, fused |
|---|---|---|---|
| GCC 14.2 | 8387 | **904,702,727** | **893,649,842** |
| GCC 16.1 | 8867 | 913,941,808 | 901,176,329 |

14.2 → 16.1 put 1.0% back on the dynamic instruction count while growing static code 5.7%. That is
what "nobody is optimizing for this" looks like from the outside: two years of compiler work is
noise against an objective it does not have. The interpreted scores — 2415 and 2417 — do not resolve
the two from each other at all, which is why the dispatch column is the one to read.

## 3.6 Where the GCC/LLVM difference actually is

Both CoreMark binaries disassembled and compared per function. An earlier version of this section
concluded that LLVM lost the dispatch count in the CRC chain, on branches and call boundaries. That
was measured against the system clang's optimizer rather than LLVM's — see §5.5 — and it does not
survive.

What is true with LLVM's own optimizer is close to the opposite. The CRC chain is where LLVM *wins*,
because `HashRecognize` turns each bit-at-a-time loop into a table lookup:

| function | GCC 14.2 | LLVM |
|---|---|---|
| `crcu8` | 66 instructions | **9** |
| `crcu16` | 131 | **14** |
| `crcu32` | 261 | **28** |
| `crc16` | 132 | **15** |

It runs over every byte of benchmark data, so that is most of LLVM's 13% dispatch advantage.

Most of the *size* difference is still cold, as it was before. `ee_printf`, `number` and `cvt` —
CoreMark's own result formatting, which runs once at the end — are 3701 instructions under GCC 14.2
and 1313 under LLVM, so the headline "39% less code" is far smaller once the reporting path is set
aside.

## 4. Processor models

`generic-rv64`, the rustc default for RV64, maps to `SpacemitX60Model`. Changing only `cpu` in the
target definition, same source, same features. Models marked † additionally needed
`-d,-f,-zcd,-v,-zve*,-zvl*,-zvbb,-zvkb,-zvfh*,-zfh*,-zfa,-xsfvcp`, since the contract ISA has no
floating point and the verifier rejects any instruction it cannot decode — the failure reads
`Error: InvalidInstruction { instruction: 3439620183 }`, opcode `0x57`, OP-V.

| cpu | scheduling model | fusable pairs | hashing dispatches | verify dispatches |
|---|---|---|---|---|
| generic-rv64 | SpacemitX60 | 155 | 14086 | **646244** |
| rocket-rv64 | Rocket | **243** | **12662** | 708340 |
| spacemit-x100 † | SpacemitX100 | — | 12902 | 691866 |
| sifive-p670 † | SiFiveP600 | — | 14086 | 655194 |
| tt-ascalon-x † | TTAscalonX | — | 14518 | 655282 |
| sifive-u74 † | SiFive7 | 64 | 14278 | 660343 |
| veyron-v1 † | NoSchedModel | 152 | 14614 | 729426 |

`xt-c920v2` could not be made to build at all. Adjacent pairs with a dead intermediate range from
**98 to 374** across these models on identical source.

Wall clock, threaded dispatch, median of three runs, for the two most interesting rows:

| | generic-rv64 | rocket-rv64 |
|---|---|---|
| hashing, unfused | 13.61 µs | 16.11 µs |
| hashing, fused | **12.99 µs** | 13.43 µs |
| verify, unfused | 696.8 µs | 767.4 µs |
| verify, fused | **664.9 µs** | 765.6 µs |

Two things fall out. `rocket-rv64` runs 10% fewer dispatches on hashing and is 3.4% slower, so
dispatch count is not the whole cost function. And under `rocket-rv64`, where there are 243 fusable
pairs instead of 155, fusion *is* resolvable in wall clock — 16.11 → 13.43 µs, −16.6%, same sign and
magnitude in all three runs. The effect is real whenever there is enough of it.

## 5. Tooling

### 5.1 Building the C workload with LLVM instead of GCC

The wrapper that used to be here ran `clang -O3 -S -emit-llvm` and then a separately chosen `llc`,
so only instruction selection came from the LLVM under test. Everything the mid-level optimizer
decides — inlining, unrolling, loop idiom recognition — came from whichever `clang` the system had.
That is how the GCC/LLVM comparison came out backwards; §5.5 has the correction. **Use §5.7's
wrapper**, which hands both `opt` and `llc` to the LLVM under test and leaves clang as a frontend
only.

### 5.2 Newer RISC-V GCC

`gcc-riscv64-unknown-elf` 14.2.0 is in questing's `universe` and can be unpacked with `dpkg -x` and
used from its own prefix. GCC 14 emits an ISA string binutils 2.42 rejects, so
`binutils-riscv64-unknown-elf` 2.43.1 has to be unpacked alongside and put on `PATH` ahead of the
system one. It ships the full multilib set including soft-float `rv64im/lp64`, so nothing else is
needed:

```bash
for f in pool/universe/g/gcc-riscv64-unknown-elf/gcc-riscv64-unknown-elf_14.2.0+19_amd64.deb \
         pool/universe/b/binutils-riscv64-unknown-elf/binutils-riscv64-unknown-elf_2.43.1-4ubuntu1+7_amd64.deb; do
  curl -sSO "http://archive.ubuntu.com/ubuntu/$f"
done
dpkg -x gcc-riscv64-unknown-elf_*.deb gcc14
dpkg -x binutils-riscv64-unknown-elf_*.deb gcc14
# then invoke gcc14/usr/bin/riscv64-unknown-elf-gcc with gcc14/usr/bin ahead on PATH
```

Newer still: riscv-gnu-toolchain publishes prebuilt nightlies, which is where GCC 16.1.0 with
binutils 2.47 came from. The assets are named without a date —
`riscv64-elf-ubuntu-24.04-gcc.tar.xz` under
`https://github.com/riscv-collab/riscv-gnu-toolchain/releases/download/<tag>/` — and `<libc>` is one
of `elf`, `glibc`, `musl`, `uclibc-ng`, `elf-picolibc`, per `.github/workflows/build-reusable.yaml`.

**It ships a single `rv64gc/lp64d` multilib**, so linking a soft-float `-mabi=lp64` program against
its own libgcc fails with `can't link double-float modules with soft-float modules`. The workaround
is to point `-L` at the soft-float libgcc of a toolchain that has one:

```bash
SOFT=$(<gcc14>/bin/riscv64-unknown-elf-gcc -march=rv64imc_zba_zbb_zbs -mabi=lp64 \
         --print-libgcc-file-name)
exec env PATH=<nightly>/bin:$PATH <nightly>/bin/riscv64-unknown-elf-gcc -L$(dirname "$SOFT") "$@"
```

All of CoreMark is still compiled by the nightly; only the double-precision helpers behind its `%f`
reporting, which run once at the end, come from elsewhere, so 14.2 and 16.1 link the same libgcc
and are directly comparable.

## 5.5 The GCC/LLVM comparison was measuring the system clang, not LLVM

§5.1's old wrapper ran `clang -O3 -S -emit-llvm` and then a separately chosen `llc`. Only *codegen*
came from that `llc`; every mid-level decision — inlining, unrolling, loop idiom recognition — came
from whichever `clang` the system had. The rows that were labelled with the `llc`'s version were the
system clang's optimizer with a newer instruction selector bolted on, and the conclusion they
supported was backwards.

Rebuilt so that both `opt` and `llc` come from the LLVM under test, with clang reduced to a frontend
(`-Xclang -disable-llvm-passes`), CoreMark at a fixed 1000 iterations, the mid-level optimizer is
worth **361,209,670 → 262,392,204 dispatches**, a 27% difference on identical source, for
essentially identical static size (5098 versus 5073 instructions).

The control that pins it: routing the *same* system clang through its own `opt -O3` and then the
newer `llc` reproduces the old number to nine significant figures, 361,209,679. So it is the version
of the mid-level optimizer, not the shape of the pipeline, and not anything the wrapper does.

Most of the difference is one transform: LLVM's `HashRecognize` analysis identifies CoreMark's
bit-at-a-time CRC loops and `LoopIdiomRecognize` replaces them with a 256-entry `.crctable` lookup.
`crcu8` goes from 66 instructions to 9, `crcu16` from 131 to 14, `crcu32` from 261 to 28, `crc16`
from 132 to 15. The older optimizer has no such transform and its output contains no `.crctable`.

That also retires §3.6. The branchless mask arithmetic GCC produced for `if (data & 1) crc ^= poly`
is no longer the interesting comparison, because LLVM does not compile that loop at all any more.

The procedural lesson: **name the binary that made each decision, not the toolchain it came from.**

## 5.6 What an interpreter-targeted CPU is worth

`generic-interpreter-rv64` in `llvm/lib/Target/RISCV`, measured against `generic-rv64` with the same
LLVM doing both mid-level and codegen, same source, same guest ISA (`rv64imc_zba_zbb_zbs`), CoreMark
at a fixed 1000 iterations. One run of §5.7's script, on a machine with the benchmark pinned to a
fixed core — without that pinning the scores moved enough to invent effects that were not there, as
the note at the end of this section records. `w/fusion` is the interpreter's own adjacent-pair
fusion enabled.

| | static | fusable pairs | dispatches | dispatches w/fusion | Iter/s | Iter/s w/fusion |
|---|---|---|---|---|---|---|
| GCC 14.2 | 8387 | 30 (0.36%) | 301,590,416 | 297,906,310 | 2775.14 | 2801.28 |
| LLVM `generic-rv64` | 5077 | 79 (1.56%) | 262,393,682 | 261,145,687 | 3254.78 | 3244.07 |
| LLVM `generic-interpreter-rv64` | **5030** | **153 (3.04%)** | **249,328,139** | **230,659,212** | 3380.42 | **3936.88** |

**−5.0% dispatches against the same compiler tuned for hardware, −12.1% with the interpreter's
instruction fusion on top, +21.0% on the interpreted score best build against best build — and 47
instructions *smaller* than the hardware tuning, not larger.** Against GCC 14.2 it is −17.3%, −23.5%
and **+40.5%**, at 40% less code. All rows produce `crcfinal 0xd340`, which the script checks.

This is the configuration with the inlining and unrolling limits left neutral, which is what §5.6's
decomposition called the free part and what the patch now defaults to. Raising them reaches
−16.6%/−23.5% and +32% code; why that is no longer the default is the ed25519 result below.

**Dispatches do not convert to wall clock 1:1.** −5.0% dispatches would be +5.3% if every dispatch
cost the same, and with fusion off it is +3.9%. With fusion on, −12.1% would be +13.7% and it is
+21.0% — better than predicted, because a fused pair removes a decoded-stream entry as well as a
dispatch. The dispatch count remains the metric that reproduces, not the metric being optimized.

### Fusion is worth a fifth of the score, and only here

| | dispatches removed by fusion | score change |
|---|---|---|
| GCC 14.2 | −1.22% | +0.94% |
| LLVM `generic-rv64` | −0.48% | −0.33% |
| LLVM `generic-interpreter-rv64` | **−7.49%** | **+16.5%** |

On hardware-tuned code the interpreter's fusion pass is a wash in both directions — its
per-instruction overhead and the 0.5-1.2% of dispatches it removes cancel. On interpreter-targeted
code it is worth 16.5%, which is four times what the codegen change is worth on its own. **The
fusion tune features are not a bonus on top of the dispatch reduction; they are what makes running
the fusion pass worth it at all**, and a deployment that runs hardware-tuned guests gains nothing by
enabling it.

> An earlier run of this same table, on an unpinned machine, showed fusion at −3.7% and −4.9% on the
> two hardware-tuned rows, and this section concluded it was a net loss there. It was noise. The
> conclusion that matters — fusion pays only on interpreter-targeted code — survives at four times
> the margin, but the claim that it actively hurts elsewhere does not, and scores from an unpinned
> core should not have been written down as effects.

### Which pairs fuse

The fused dispatch column is **the interpreter's own fusion pass**, not LLVM's: it folds any
adjacent pair matching its rule, whether or not LLVM has a corresponding fusion definition. LLVM's
tune features mostly fuse nothing - `Fusion` records become `SDep::Cluster` edges in the machine
scheduler, so what they change is how often the interpreter's patterns end up adjacent. Two are not
scheduling at all: `hasConditionalMoveFusion()` gates select lowering in `RISCVISelLowering.cpp`,
and `hasAUIPCADDIFusion() && hasLUIADDIFusion()` changes address cost in TTI. This page said they
were all scheduling edges, which is why disabling the machine scheduler was wrongly expected to
neutralise them. The 219 pairs in the
interpreter build break down as:

| pair | count | LLVM tune feature |
|---|---|---|
| `auipc`+`addi` | 65 | `auipc-addi` |
| `sh[123]add(.uw)`+load | 58 | `shxadd-load` |
| branch+`c.mv` | **48** | `conditional-cmv-fusion` |
| `slli`+`srli`(`.uw`) | 15 | `bfext`, `shifted-zext` |
| `add`+load/store | 14 | `add-load`; the store half has no feature enabled |
| `addi`+`addi` | **9** | **none - interpreter only** |
| `auipc`+`ld` | 5 | `auipc-load` |
| `and`/`andi`+`or`/`andi` | 5 | `logic-reg-reg`, `logic-reg-imm` |

(The breakdown above was taken from a build with the inlining and unrolling limits raised, which
had 219 fusable pairs against the 153 of the table in the previous section. The proportions are
what to read.)

Two things fall out. Branch+`c.mv` is 22% of all fusable pairs and comes entirely from the one tune
feature added last; before it there were 168 pairs, not 219. And `addi`+`addi` fires nine times with
no LLVM help at all, which is the direct argument for the three `SimpleFusion` records proposed in
`interpreter-targeted-codegen.md` §9 - the other two of those, `addi`+`sh[123]add` and
`xor`+`rori(w)`, do not appear in CoreMark at all, but §2.2 measures them as the two most common
pairs in real contract code.

### Where it comes from, and what it costs in code size

Each row is the interpreter CPU with one thing changed, so the column reads as what that thing
contributes. Static code is the second objective and most of this is bought with it — except the
first row, which is not.

| configuration | dispatches | dispatches, fused | static |
|---|---|---|---|
| `generic-rv64` | 262,392,476 | 261,145,223 | 5070 |
| interpreter CPU, inlining ×1, max unroll 1 | 249,326,777 | **230,658,643** | **5022** |
| interpreter CPU, max unroll 1 | 229,886,682 | 211,218,280 | 5549 |
| **interpreter CPU (max unroll 2)** | **218,980,659** | **200,836,423** | **6703** |
| interpreter CPU, max unroll 3 | 215,736,970 | 197,368,744 | 8477 |

Rows measured before the shift-chain rule and `conditional-cmv-fusion` went in, kept because they
are the evidence for the cap: max unroll 4 was 217,740,387 at 8923 instructions and **uncapped was
223,308,441 at 12756** — worse than 3 on both axes, because the register pressure of a body unrolled
by 8 costs more in spills than the backedges it removed. `matrix_sum` under that build spills twelve
callee-saved registers on entry.

- **The first row is free, and it is the one worth having first.** The scheduling model, the fusion
  tune features, `conditional-cmv-fusion`, the shift-chain unrolling rule, the branch pricing and
  the disabled latency heuristic, with both multipliers neutralized, produce **less** code than
  `generic-rv64` — 5022 against 5070, 0.9% smaller — and **5.0% fewer dispatches, 11.7% fewer after
  fusion**. Smaller and faster at once. If only one thing here is taken, take this.
- **The interpreter scheduling model is what earns that**, not the branch pricing. The last row is
  the same tuning on `generic-rv64`'s hardware scheduling model and without the fusion features: it
  is marginally *better* on raw dispatch count (224,853,631) and much worse after fusion
  (224,110,370), with 87 fusable pairs instead of 168. Counting the wrong thing would have thrown
  the scheduling model away.
- **`conditional-cmv-fusion` is the second free thing, and it is also strictly Pareto.** A select
  becomes `bcc +6; c.mv` rather than a branch diamond or, where Zicond is available, a three
  instruction `czero`/`czero`/`or`; and the interpreter fuses exactly that pair
  (`FusedBeqCMv`/`FusedCBeqzCMv` in `fused/rv64/zca.rs`) into one dispatch. Worth −0.7% raw,
  **−1.7% after fusion, at 0.3% less code**, and it takes fusable pairs from 168 to 219. It is inert
  without Zca, so it costs nothing where compression is off. Note that §3 measured it as roughly a
  wash on the contract workloads under the old configuration; this is CoreMark under the
  interpreter CPU, and it is one line to drop if a workload disagrees.
- **Inlining ×2 is −7.5% for +11% static code**, and it plateaus: ×3 changes no counts and adds
  another 9% of code.
- **Unrolling by a fixed factor is the rest, and 2 is the right cap.** It is −4.7% for +21% static
  code. Going to 3 buys a further 1.5% for another 26% of code, which is the point at which the
  trade stops being worth it — and 4 and uncapped are worse than 3 on both axes.
  `-mllvm -riscv-interpreter-max-unroll-count=N` moves along that frontier.
- **Unrolling a shift chain to its period is the exception, and it is nearly free.** A loop that
  does `next = list; list = list->next;` needs no copies inside an unrolled body but one per link
  at the backedge, and only unrolling to the chain's period makes that assignment the identity.
  `core_list_reverse`, inlined into `core_bench_list`, is the single hottest loop in the benchmark
  at 10.9% of all dispatches, and a fixed cap of 2 cut its period-3 chain short and left a copy per
  node. Unrolling it to 3 is **−2.7% of the whole program for seven static instructions**. `mv` was
  5.8% of all dispatches before this.

Three further tune-only changes were measured and are **not** in the CPU, because on this workload
they do nothing: `+fusion-logic-imm-reg` and `+fusion-add-mem` (both implemented by the interpreter,
but CoreMark contains none of those pairs — the contract workloads might, which is where to look
next), and lowering `MinimumJumpTableEntries` to 2. `+unaligned-scalar-mem` is dispatch-neutral here
and 0.2% smaller, but it is a claim about the consumer's memory model rather than about tuning, so
it belongs in the target definition — where this repository already sets it — and not in the CPU.

### The same thing at `-O2`

Rust contracts are built at `-O3` with fat LTO and one codegen unit, but C is more often `-O2`, so
the tuning has to hold there. It does, slightly better in relative terms:

| `-O2` | static | dispatches | dispatches, fused |
|---|---|---|---|
| LLVM `generic-rv64` | 4870 | 267,728,866 | 266,496,586 |
| LLVM `generic-interpreter-rv64` | 6432 | **221,279,223** | **203,134,723** |

−17.4% and −23.8%, against −16.6% and −23.5% at `-O3`.

It is also a point on the frontier in its own right — 6432 instructions against 6703, for 1% more
dispatches — but the 1% is not free, and this is the one place where dispatch count alone would have
been misleading in the cheap direction. Timed: **`-O2` is 1.9% slower, ±0.9%**, over 35 rounds of
the two builds run alternately at 4000 iterations, faster in 5 of them (sign test p < 0.0001). The
extra dispatches cost about twice their share, so the instruction mix is worse and not just longer.

`-O2` therefore buys 4% of code for 2% of speed. That is a real trade to make when size is binding,
but it is a trade. `-Os` is not on the frontier at all: it turns off the CRC recognition that is
worth more than everything in this document put together.

Resolving 2% took a method, since the run-to-run spread on identical binaries is 2.7-3.1%: run the
two builds **alternately**, one pair per round, and take the per-round difference, so that whatever
the machine is doing drifts out of both halves equally. 35 paired rounds put two standard errors at
0.9%. Fifteen were not enough to be comfortable, and a single pair is worthless.

Unrolling more is not a free lunch even before the size cost. Disabling it entirely costs +4.1%
dispatches for 247 fewer static instructions, so the sign the handoff left open is settled —
**unrolling helps, counted** — but only up to a factor the register file can absorb, and the
interpreted score stops improving well before the dispatch count does.

### Does it generalize to the contract workloads? No — it inverts

It does not, and finding out changed the defaults. Built with a patched rustc, `generic-rv64` before
and `generic-interpreter-rv64` after, everything else on `main`, so no interpreter-side fusion:

| workload | before | after | change |
|---|---|---|---|
| `blake3_hash_chunk` | 16.35 µs | 16.38 µs | **−5.4%** (−9.2% … −1.1%), p = 0.03 |
| `ed25519_verify` | 689 µs | 1137 µs | **+63.9%** (+61.6% … +66.5%), p = 0.00 |

Blake3 improves. ed25519 runs **64% slower**, and the guest `.text` went from 20,120 to 73,784
bytes — 3.67×, against the +32% CoreMark showed.

Almost all of it is one function. `FieldElement51::pow22501`, the field inversion, went from **248
bytes to 17,436** — 70× — and `pow2k`, a 480-byte loop of one 5-limb squaring per iteration, vanished
from the binary:

| | before | after |
|---|---|---|
| `pow22501` instructions | 98 | 5731 |
| multiplies in it | 0 (all in `pow2k`) | 1162 |
| spill stores / reloads | 5 / 5 (in `pow2k`) | **454 / 475** |
| backedges | 0 | 6 |

The chain is mechanical. `pow22501` calls `pow2k` seven times with a literal count — 5, 10, 20, 10,
50, 100, 50, so 245 squarings. Raising the inlining threshold pulled `pow2k` into each call site,
which turned each trip count into a constant, which let the unroller at it; 1162 multiplies at 30
per squaring is 39 squaring bodies laid out where there had been one. A 5-limb squaring already uses
most of the register file, so the unrolled bodies spill: **454 spill stores per call where there had
been five.**

Those spills are the cost. A spill is one dispatch like any other, but it is a *guest memory
access* — the most expensive kind in §5.6's own cost model — and it replaced an `addi` and a
backedge. The dispatch count barely notices; the clock does. The decoded stream compounds it: at 8
host bytes per 4 guest bytes, this workload's footprint went from about 40 KB, which fits a typical
L1d, to about 147 KB, which does not, and a pre-decoding interpreter walks that as data.

**So §4's warning has a sharper form than the one this page had been repeating.** Dispatch count is
not merely an attenuated predictor of wall clock; here it pointed the wrong way. The prediction was
made on this very page:

```bash
AB_EXTRA_RUSTFLAGS="-Cllvm-args=--inline-threshold=450" \
  cargo run --release -p ab-riscv-benchmarks --example dispatch_count
```

| | baseline | `--inline-threshold=450` |
|---|---|---|
| `blake3_hash_chunk` | 14583 | 14583 |
| `ed25519_verify` | 654763 | 638558 (−2.5%) |

−2.5% dispatches, +64% time. Counting dispatches is still the only thing that resolves a 1% change,
but it has to be read with the static size and the spill count beside it, and a build that grows
code by more than a few tens of percent has to be timed before it is believed.

### What changed as a result

The two knobs responsible now default to neutral, so what `generic-interpreter-rv64` does
unconditionally is the scheduling model, the branch pricing and the fusion tuning:

| knob | was | now |
|---|---|---|
| `-riscv-interpreter-inlining-threshold-multiplier` | 2 | **1** |
| `-riscv-interpreter-max-unroll-count` | 2 | **1** |

Both remain available for sweeping a particular consumer:
`-Cllvm-args=-riscv-interpreter-inlining-threshold-multiplier=2
-Cllvm-args=-riscv-interpreter-max-unroll-count=2` restores the old behavior without rebuilding
rustc. §5.6's table is the new default measured; it is smaller than `generic-rv64` and faster on
every axis, so nothing was given up on CoreMark to get here.

The shift-chain rule is untouched: it fires on loops that are already small and register-light, and
Blake3's `compress_in_place` got 84 bytes *smaller* in the same build.

### What is left: the scheduling model spills multiply-heavy code

With the limits neutral, the guest binary is now 19,982 bytes of `.text` against `generic-rv64`'s
20,120 — slightly *smaller* — and Blake3 is unchanged within noise. ed25519 is still **15.8% slower**
(+14.2% … +17.7%, p = 0.00, pinned core).

Same size, same instructions, worse time. The difference is where the instructions are:

| function | multiplies | spill st/ld, `generic-rv64` | spill st/ld, interpreter |
|---|---|---|---|
| `FieldElement51::mul` | 50 | 5 / 10 | **32 / 37** |
| `Scalar52::montgomery_mul` | 50 | 2 / 8 | **39 / 10** |
| `pow2k` (squaring) | 30 | 5 / 5 | **11 / 11** |
| `ProjectivePoint::double` | 0 | 25 / 30 | 26 / 31 |
| `EdwardsPoint + ProjectiveNiels` | 0 | 30 / 30 | 30 / 30 |
| `EdwardsPoint − ProjectiveNiels` | 0 | 34 / 34 | 30 / 30 |
| Blake3 `compress_in_place` | 0 | 17 / 49 | 18 / 42 |

**Every function with multiplies gained spills; every function without them did not.** The
correlation is exact, and the two worst are the hottest functions in ed25519: `FieldElement51::mul`
grew 58 instructions, 54 of which are spill traffic, for the same 50 multiplies.

The cause is the scheduling model itself. `generic-rv64` has none, so the pre-RA machine scheduler
has nothing to schedule for and stays close to source order. `InterpreterModel` gives it a model,
and it does what a scheduler does: reorders for the machine it is told about, lengthening live
ranges. A 5×5-limb schoolbook multiply produces 50 partial products and already wants the whole
register file, so any lengthening spills — and a spill is a guest memory access, the most expensive
dispatch there is. CoreMark never showed this because CoreMark barely multiplies.

This is the awkward part of §5.2's premise. The model exists to say that dispatches cost different
amounts, which is true and which `llvm-mca` and the cost queries want. But the same model is what
the scheduler reads, and an interpreter has no pipeline: it executes one dispatch at a time to
completion, so the total cost of a basic block does not depend on the order at all. There is nothing
for a scheduler to win here and register pressure to lose, which suggests the model should be
telling the scheduler to leave the order alone rather than describing a machine.

The three `AB_GUEST_*` runs first attempted here were the same binary measured three times — the
checkout predated the variables, so they were ignored and the CPU came from a hand edit. Their
spread is worth keeping: **801.97, 821.77 and 824.82 µs for one identical binary on one pinned core,
2.8% between the extremes.** That is the noise floor, and it is wider than most of the effects here.
Re-run properly, the picture is clean:

| guest build | ed25519 | vs the control |
|---|---|---|
| `generic-rv64` **+ `+interpreter-target`** (control) | 700.24 µs | — |
| `generic-interpreter-rv64` | 809.56 µs | **+15.6%** |
| …`-enable-post-misched=false` | 805.79 µs | +15.1% |
| …`-riscv-force-machine-combiner-strategy=min-instr` | 811.15 µs | +15.8% |
| …`-enable-misched=false` | 763.77 µs | **+9.1%** |

**The control settles the confounds.** `generic-rv64` with the interpreter tuning added, built by the
patched rustc and measured on the pinned core, lands at 700 µs — the same as the original baseline.
So the baseline was valid after all: the stage 2 compiler agrees with the stock nightly, and the
pinned core agrees with whatever ran before it. It also means:

- **The `interpreter-target` tuning feature costs nothing.** −0.5%, p = 0.56. The expensive-jump
  pricing, `getPredictableBranchThreshold() == 1` and the mispredict penalty are all free here.
- **The whole 15.6% belongs to the CPU's other half**, and the pre-RA machine scheduler accounts for
  only 6 of it.

### `conditional-cmv-fusion` is not it either

| guest build | ed25519 | vs a 687 µs baseline |
|---|---|---|
| `generic-rv64` (pinned baseline) | 687.11 µs | — |
| `generic-interpreter-rv64` | 809.56 µs | +17.8% |
| …`AB_GUEST_FEATURES=-conditional-cmv-fusion` | 790.51 µs | **+15.1%** |
| …`-enable-misched=false` | 763.77 µs | +11.2% |
| `generic-rv64` + `+interpreter-target` | 700.24 µs | +1.9% |

Subtracting the feature is worth about 2.4 points of the 17.8, so the reasoning — that it suppresses
the branchless `czero` lowerings in instruction selection, which no scheduler flag can undo — was
right about the mechanism and wrong about the magnitude. It is a small real cost on a build that
does not fuse, not the missing nine.

That makes three hypotheses tested and three mostly wrong: `MachineCombiner`, the tuning feature,
and this. What is actually established is short:

- the `interpreter-target` tuning feature is free (+1.9%, and it is the control);
- the pre-RA machine scheduler is worth about 6 points;
- `conditional-cmv-fusion` is worth about 2.4;
- **about 9 points remain unattributed**, and the post-RA scheduler, `MachineCombiner`, the
  SelectionDAG scheduler and early if-conversion are each ruled out.

The pinned baseline also retires a theory about the measurement rather than the code: 687.11 µs
pinned against 689.34 µs unpinned. Pinning changes nothing here, so the earlier unpinned runs are
comparable after all and the core switch never explained anything.

### The mechanism, from three binaries built by one compiler

`generic-rv64`, `generic-interpreter-rv64`, and the same with `-enable-misched=false`, all from the
stage 2 rustc. Spill stores and reloads per function:

| function | multiplies | `generic-rv64` | interpreter | interp, no misched |
|---|---|---|---|---|
| `FieldElement51::mul` | 50 | **5 / 10** | 32 / 37 | 23 / 28 |
| `pow2k` | 30 | **5 / 5** | 11 / 11 | **5 / 5** |
| `ProjectivePoint::double` | 0 | 25 / 30 | 26 / 31 | 27 / 32 |
| `EdwardsPoint ± ProjectiveNiels` | 0 | 30/30, 34/34 | 30/30, 30/30 | 32/32, 35/35 |
| Blake3 `compress_in_place` | 0 | 17 / 49 | 18 / 42 | 17 / 47 |
| sha512 `compress512` | 0 | 3 / 8 | 3 / 8 | 3 / 8 |

`.text` totals 20,120, 19,982 and 19,714 bytes: the regression is not size, and the interpreter build
is the *smaller* one. Only multiply-heavy functions move, `pow2k` returns exactly to baseline once
the scheduler is off, and `FieldElement51::mul` returns only two thirds of the way.

The layout says why. In `FieldElement51::mul`:

| build | instructions | multiplies span | stack stores | first spill at |
|---|---|---|---|---|
| `generic-rv64` | 195 | indices **18 … 152** | **0** | — |
| interpreter | 253 | 10 … 97 | 27 | index 12 |
| interp, no misched | 234 | 17 … 104 | 18 | index 48 |

`generic-rv64` spreads its 50 multiplies across 134 instructions, interleaving each product with its
consumer, and spills nothing at all. Both interpreter builds compress the multiplies into a band of
exactly **87** instructions — the same width with the machine scheduler on and off. So the
compression is not the machine scheduler. Fifty products come live at once, the register file cannot
hold them, and the spills follow; the machine scheduler then adds nine more on top, which is the six
points it is worth.

The instruction counts confirm it is a reordering rather than different code: 195 against 234 is 39
more instructions, of which 36 are the 18 spill stores and 18 reloads.

**This is the first evidence that names a quantity rather than a pass**, and it inverts the premise
in §5.2. A non-uniform per-dispatch cost model exists to say that a multiply costs more than an add.
Whatever consumes that statement responds by moving multiplies away from their consumers, which is
the right answer for a pipeline with something else to do in the meantime and the wrong one for an
interpreter, which has nothing else to do and pays for the spills instead. An interpreter's block
cost does not depend on order, so a model that provokes reordering can only lose.

### It is the latencies, and `generic-rv64` was never model-less

A fourth build, with `-Cllvm-args=-schedmodel=false`, does **not** restore the baseline:

| build | `.text` | `FieldElement51::mul` | multiply span | stack stores |
|---|---|---|---|---|
| `generic-rv64` | 20,120 | 195 insts | **134** | **0** |
| `generic-interpreter-rv64` | 19,982 | 253 | 87 | 27 |
| …`-enable-misched=false` | 19,714 | 234 | 87 | 18 |
| …`-schedmodel=false` | 19,684 | 234 | **84** | 18 |

Taking the scheduling model away from every consumer leaves the compression exactly where it was.
So the model is not the cause — and the reason is a fact this page had wrong throughout:
**`generic-rv64` is not model-less.** It is
`RISCVProcessorModel<"generic-rv64", SpacemitX60Model, …>`, a full hardware model. The comparison
was never "a model against no model"; it was **SpacemitX60's latencies against `InterpreterModel`'s,
and `-schedmodel=false` replaces the second with no latencies at all**, which behaves like the
second, not like the first.

That identifies the quantity. `InterpreterModel` declared **latency 1 for everything**, on this
argument, written in its own header:

> Latency 1 everywhere, because a handler completes before the next dispatch begins. There is no
> dependency distance to hide, so the scheduler is left to minimize register pressure.

The second sentence does not follow from the first. With every latency equal there is nothing
telling a scheduler to keep a producer near its consumer, so it packs the expensive instructions
together — and fifty partial products come live at once. SpacemitX60 says a multiply takes several
cycles, the scheduler interleaves each product with its consumer to cover that, and the live ranges
stay short as a side effect. Minimising register pressure is not what a scheduler does when told
nothing; it is what latency happened to buy here.

The fix is in the model rather than in any pass, which is consistent with the compression surviving
both `-enable-misched=false` and `-schedmodel=false`: **latency now equals the per-dispatch cost.**
A multiply is charged three units of latency as well as three of occupancy, a load two, a division
eight. That is also the more honest statement — the result is not available until the handler has
run, and the handler costs three dispatches worth of time. The two quantities were always the same
number and only one of them was being reported.

**Tested twice, and neither prediction held.** With latency equal to the dispatch cost, and then
additionally with `-disable-latency-sched-heuristic` so the scheduler would read those latencies,
`FieldElement51::mul` comes out byte for byte the same every time:

| build | `FieldElement51::mul` | multiply span | stack stores |
|---|---|---|---|
| `generic-rv64` | 195 insts, 594 B | **134** | **0** |
| interpreter, latency 1 | 253, 724 B | 87 | 27 |
| interpreter, latency = cost | 253, 724 B | 87 | 27 |
| …and the latency heuristic re-enabled | **253, 724 B** | **87** | **27** |

The binaries differ, so the flags took effect; this one function does not. Four hypotheses have now
been tested and four have failed: `MachineCombiner`, the `interpreter-target` tuning feature,
`conditional-cmv-fusion`, and the latency pair. Each was arrived at by reading LLVM for something
that could plausibly produce the effect, and that method has a hit rate of zero here.

What the measurements actually pin down is narrow and worth stating on its own:

- the compression survives `-enable-misched=false`, `-schedmodel=false`, `-riscv-force-machine-
  combiner-strategy=min-instr`, a latency model, and the latency heuristic. **It is not the
  scheduling model and not any scheduler.**
- `generic-rv64` with `+interpreter-target` runs at baseline speed, so the tuning hooks are clear —
  though that was a timing result and the band in that binary has never been looked at.
- that leaves the seventeen fusion tune features, which have never been isolated.

### Bracketed: it is the scheduling model, and the reason is latency against occupancy

| build | `FieldElement51::mul` | multiply span | stack stores |
|---|---|---|---|
| `generic-rv64` | 195 insts, 594 B | **134** | **0** |
| `generic-interpreter-rv64` | 253, 724 B | 87 | 27 |
| A: the CPU, all seventeen fusion features subtracted | 253, 724 B | 87 | 27 |
| B: `generic-rv64` + `interpreter-target` | **195, 594 B** | **134** | **0** |

A is unchanged, so it is not the fusion features. B is identical to the baseline, so it is not the
tuning feature either. Between them they leave exactly one thing: **the scheduling model**, which
this page ruled out one section ago on bad reasoning. `-schedmodel=false` was read as "the model is
not the cause" when what it shows is that *no* model behaves like `InterpreterModel` and neither
behaves like `SpacemitX60Model`. Those are different statements, and only the second is supported.

The two models differ in the way that matters:

| | `SpacemitX60Model` | `InterpreterModel` |
|---|---|---|
| `IssueWidth` | 2 | 1 |
| `WriteIMul` latency | **6** | 3 |
| multiply resource occupancy | brief, one of several units | **3, the single serial slot** |

A scheduler spreads a producer away from its consumer only when there is a *gap* to fill — when
latency exceeds the time the instruction occupies its resource. SpacemitX60 says a 64-bit multiply
occupies an issue unit briefly and produces its result six cycles later, so there are six cycles of
slack and the scheduler fills them with the next product's address arithmetic, which is why all 50
multiplies end up interleaved with their consumers across 134 instructions and nothing spills.

`InterpreterModel` says a multiply occupies the one serial dispatch slot for three cycles and
produces its result after three. **Occupancy equals latency, so the gap is exactly zero**, and the
consumer can issue the instant the producer retires. There is nothing to fill, no reason to
separate anything, and the multiplies pack together.

Setting latency equal to the dispatch cost, which this page did one section ago, is therefore
precisely the value that guarantees no spreading — which is why that change came out byte for byte
identical. The earlier `Latency = 1` had the same property for the same reason.

That is an uncomfortable result rather than a fix. A single serial resource whose occupancy is the
dispatch cost is the *correct* model of an interpreter, and it is what `llvm-mca` needs to report
dispatch counts. It is also, unavoidably, a model with no slack anywhere, and a scheduler given no
slack leaves every value live.

### Confirmed, and it runs the other way round

| build | `FieldElement51::mul` | multiply span | stack stores | ed25519 |
|---|---|---|---|---|
| `generic-rv64` | 195 insts, 594 B | **134** | **0** | 687 µs |
| `generic-rv64`, `-enable-misched=false` | **234, 690 B** | **87** | **18** | 733 µs (+6.7%) |
| `generic-interpreter-rv64`, `-enable-misched=false` | **234, 690 B** | **87** | **18** | 764 µs |
| `generic-interpreter-rv64` | 253, 724 B | 87 | 27 | 809 µs (+17.8%) |

**With the machine scheduler off, the two CPUs produce identical code** — the same 234 instructions,
the same band, the same 18 spills, the same 690 bytes, and `pow2k` identical too. Everything that
separates them is what the scheduler does with their respective models.

That reverses the description this page has been using. The interpreter build does not *compress*
anything: the 87-wide band with 18 spills is what the code looks like before any scheduling, and
`SpacemitX60Model` is what **spreads** it out to 134 and removes every spill. `InterpreterModel`
fails to spread it and then adds nine more spills of its own.

So the model is worse than useless here — it is worse than having no scheduler at all:

| | vs no scheduling |
|---|---|
| machine scheduler with `SpacemitX60Model` | **−6.3%** |
| machine scheduler with `InterpreterModel` | **+10.5%** |

And the reason is the one identified above: occupancy equal to latency leaves zero slack, so the
scheduler has no gap to fill and no reason to move anything, while still being free to lengthen a
live range wherever some other heuristic prefers it.

model.

### The model, and what a second change would be

`RISCVSchedInterpreter.td` is a renamed copy of the model `generic-rv64` uses. It describes nothing
about an interpreter, and that is the point: it is the configuration that measured well, so any
deviation from it shows up as a deviation with a number attached rather than as an assumption
baked into a new file.

Nothing has been deviated yet. The candidates, in the order the evidence suggests:

- **`MispredictPenalty`**, 9 in the borrowed model. A guest branch is a host indirect jump nothing
  can predict, so the true figure is higher, and it feeds `getBranchMispredictPenalty()` and the
  if-conversion decisions rather than the scheduler.
- **`LoadLatency`**, 3 in the borrowed model. A guest load pays address arithmetic, a bounds check
  and a host memory access, which is not obviously three dispatches' worth.
- **Multiply and divide latency**, 6 and more in the borrowed model. These are what produce the
  spreading that matters, so they are the most dangerous to touch and the most interesting: the
  question is whether the right value for an interpreter is the hardware's or something larger,
  since the thing being traded away is spills rather than stalls.

Each is one line, one LLVM rebuild and one pair of benchmark runs, and each should be its own change
with its own number. What must not happen again is a whole model derived from first principles and
shipped before any of it is measured.

### A second consumer: PolkaVM, where it does nothing

PolkaVM was the obvious independent check — it already hand-assembles a version of this tuning,
and it has both an interpreter and a recompiler. Only the `cpu` field of its target specification
differs between the runs; its own macro-fusion features are enabled in both. Execution time,
excluding compilation:

| benchmark / backend | PolkaVM's tuning | + `generic-interpreter-rv{32,64}` | |
|---|---|---|---|
| pinky, 32-bit interpreter | 76.39 ms | 77.88 ms | +1.9% |
| pinky, 64-bit interpreter | 72.05 ms | 75.19 ms | **+4.4%** |
| pinky, 32-bit recompiler | 7118 µs | 7122 µs | +0.1% |
| pinky, 64-bit recompiler | 7127 µs | 7191 µs | +0.9% |
| prime-sieve, 32-bit interpreter | 52.31 ms | 50.86 ms | −2.8% |
| prime-sieve, 64-bit interpreter | 42.94 ms | 42.93 ms | −0.0% |
| prime-sieve, 32-bit recompiler | 4012 µs | 3993 µs | −0.5% |
| prime-sieve, 64-bit recompiler | 2918 µs | 2885 µs | −1.1% |

**No benefit.** The changes are small and inconsistent in sign, which on single measurements with
a noise floor around 3% means nothing is demonstrated — except possibly pinky's 64-bit
interpreter, which is 4.4% *worse*.

The reason is structural, and it is the useful part: **PolkaVM does not execute RISC-V.** Its
linker ingests the RISC-V ELF and lowers it to its own bytecode, running its own optimization
pipeline on the way — `perform_inlining`, `perform_dead_code_elimination`,
`perform_constant_propagation`, `perform_nop_elimination`,
`perform_load_address_and_jump_fusion`, `perform_meta_instruction_lowering`
(`crates/polkavm-linker/src/program_from_elf.rs`). Whatever LLVM decided about instruction
selection and adjacency is re-decided there. The interpreter and the recompiler both run that
bytecode, which is why neither moves.

So the scope of this work is narrower than "software execution targets": it is for consumers that
**dispatch RISC-V instructions directly**. Where a consumer re-compiles RISC-V into something
else first, its own middle-end is what matters and the RISC-V tuning washes out.

That makes the right independent checks libriscv and CKB-VM, both of which pre-decode and
dispatch RISC-V as-is, rather than PolkaVM.

### A third consumer: libriscv, where it does what it is supposed to

[libriscv](https://github.com/libriscv/libriscv) is the fair test of the narrowed claim: it
pre-decodes a RISC-V ELF into a threaded dispatch table and executes the instructions the compiler
emitted, with no bytecode of its own in between. CKB-VM is in the same class but its only
benchmark (`benches/bits_benchmark.rs`) measures bit-manipulation helpers rather than a guest
program, so there is nothing there to compare.

CoreMark again, but a different build of it from the one in section 5.6: libriscv wants a hosted
binary, so this one is linked against picolibc with a small ecall host interface, 40000 iterations,
CRCs validated. Only `-mcpu` differs between the two columns. Nine pinned runs each,
`libriscv@e121610`, interpreter mode:

| | `generic-rv64` | `generic-interpreter-rv64` | |
|---|---|---|---|
| guest instructions dispatched | 10 492 964 537 | 10 036 546 491 | **−4.3498%** |
| `.text` | 22 040 B | 22 144 B | +0.47% |

The instruction count is a property of the codegen, not of the VM, and it lands on exactly the
same −4.35% as our own interpreter measured on its own CoreMark build — two different CoreMark
ports, two different runners, same number. Run on a second machine it agrees to six significant
figures, and `.text` grows by the same 104 bytes. That is a useful cross-check that what section
5.6 measured is real and not an artifact of our dispatcher.

Wall clock is the part libriscv adds, and it is the part that needs a second machine and a run
long enough to outlast the host's scheduling noise. Both machines, nine pinned runs each:

| host wall clock | `generic-rv64` | `generic-interpreter-rv64` | |
|---|---|---|---|
| machine A, median of 9 | 8455.8 ms | 8223.2 ms | **−2.75%** |
| machine A, mean of middle 7 | 8450.2 ms | 8242.7 ms | −2.46% |
| machine A, fastest of 9 | 8413.3 ms | 8195.6 ms | −2.59% |
| machine B, median of 9 | 3577.5 ms | 3485.9 ms | **−2.56%** |
| machine B, mean of middle 7 | 3571.2 ms | 3486.5 ms | −2.37% |
| machine B, fastest of 9 | 3517.0 ms | 3453.5 ms | −1.81% |

Every statistic on both machines falls between −1.8% and −2.8%, so **−2.5% is the figure**. On
machine A the two sets of runs are disjoint — every interpreter run beat every baseline run. On
machine B one interpreter run (3533.0 ms) exceeds the baseline's fastest (3517.0 ms), which is why
its fastest-of-9 comparison is the weakest number in the table.

Run length matters here and the default in the script reflects it. At 8000 iterations, about
0.7 s per run on machine B, the same three statistics spanned −1.2% to −3.1% and the separation
depended on which one was quoted; the baseline's distribution carried a long upper tail (963, 765,
743 ms) that its interpreter runs lacked. At 40000 the spread closed to under one point. Nothing
about the codegen changed between those two sets of runs — only how much of the host's noise each
run averaged over.

So roughly half of the −4.35% instruction saving converts into time. Less than one-for-one, which
is what one would expect: removing an instruction removes a dispatch, but the instructions removed
are cheap ones and the ones left behind are not uniformly priced. It is still a real speedup on a
mature interpreter from a change that is a single `-mcpu` flag.

Three consumers, then, and the pattern is consistent: the tuning is worth something wherever
RISC-V is what actually gets executed (our interpreter, libriscv) and nothing where it is not
(PolkaVM, both backends).

### Corrections this forced

Three claims on this page were built on `generic-rv64` having no scheduling model, and are void:

- that `MachineCombiner` would switch strategy between the two CPUs — both have a model, so
  `getMachineCombinerTraceStrategy()` may well return the same thing for both, which is what the
  measurement showed;
- that the SelectionDAG scheduler could be ruled out by RISC-V preferring source order — true, but
  it was never the difference;
- that the pre-RA machine scheduler was the main actor, on the strength of its 6 points. It is a
  third of the effect and it sits on top of a compression that is already there without it.

The fusion tune features remain unisolated, and are now the alternative hypothesis if the latency
change does not deliver: `AB_GUEST_FEATURES` can subtract them from the CPU in one string,
`-fusion-lui-addi,-fusion-auipc-addi,-fusion-zexth,-fusion-zextw,-fusion-shifted-zextw,`
`-fusion-ld-add,-fusion-add-load,-fusion-auipc-load,-fusion-lui-load,-fusion-bfext,`
`-fusion-addi-load,-fusion-shxadd-load,-fusion-logic-reg-reg,-fusion-logic-reg-imm,`
`-fusion-mul-add,-fusion-shift-bit-extract,-conditional-cmv-fusion`.

### What the interpreter CPU actually changes, piece by piece

`generic-interpreter-rv64` at `43bde96` bundles more than its description says. Setting aside the
fusion features, which upstream already exposes, it is these, each switchable separately:

| | piece | reachable upstream as |
|---|---|---|
| J | jumps are expensive | `-jump-is-expensive` |
| S | SelectOptimize off — dropped silently, by replacing `GenericTuneFeatures` | `-mattr=-enable-select-opt` |
| A | RISC-V's own unroll preferences instead of the generic ones | `-mattr=+no-default-unroll` |
| B | partial and runtime unrolling capped at one | `-unroll-max-count=1` |
| C | a small loop unrolled to the period of a shift chain | nothing |
| D | predictable-branch threshold of one | nothing |

and three that do nothing on this base: the mispredict penalty override (`BasicTTIImpl` already
returns the model's), the inlining multiplier (1 is the default) and the cloned scheduling model.

CoreMark, every row with the fusion features on `generic-rv64`:

| | static | dispatches | fused |
|---|---|---|---|
| fusion features only | 5049 | 261,488,522 | 242,820,034 |
| + J | 5088 | +0.59% | +0.63% |
| + S, + A+B, + D, in any combination without C or J | 5049 | identical | identical |
| + A alone | 11,529 | −8.3% | −7.7% |
| **+ C** | **5064** | **−4.60%** | **−4.96%** |
| + C + J, which is the old CPU | 5103 | −4.02% | −4.33% |
| + A, cap 2 / 3 / 4 | 6178 / 7948 / 8131 | −7.0 / −10.3 / −10.5% | −6.6 / −9.6 / −9.9% |

Wall clock, ten paired rounds on a pinned core against fusion features only: C alone **+4.6%**
fused (faster in 10 of 10) and **+4.4%** unfused (9 of 10); the old CPU, which adds J, +1.2% and
+3.3%. J costs time as well as dispatches.

So on CoreMark **C is the whole effect**, and it is one loop. `core_list_reverse` rotates three
values per element, `next = list->next; list->next = prev; prev = list; list = next`, which costs
two `mv` copies at the backedge; unrolled by three the rotation is the identity and the copies
disappear, five instructions per element becoming three. Nothing upstream reaches it: the nearest
approximation, a blanket unroll cap, removes more dispatches but only by unrolling every small loop,
at 22% to 61% more code.

The contract workloads on the pinned toolchain, LLVM 23.1, with a target specification that at the
time carried all nineteen fusion features and Zicond:

| | static | `blake3_hash_chunk` | `ed25519_verify` |
|---|---|---|---|
| base | 6193 | 14,583 | 654,763 |
| + J | 6195 | same | +8 |
| + S, + A+B, + J+S, + A+B+S, + A+B+J+S | 6193 or 6195 | same | same, or +8 with J |
| + A | 6536 | same | +0.64% |
| + A, cap 2 / 3 | 6488 / 6500 | same | +0.64% |

None of the reachable pieces helps either workload. C and D need an LLVM with the patch, and
`interpreter-codegen/ablate-rust.sh` runs them against the rustc from `build-patched-rustc.sh`.

With that rustc, the rows that differ only in C and D come out the same as base in every count:
6193 static instructions and 654,763 `ed25519_verify` dispatches whether C and D are on, only D is
on, or neither is. Neither workload has a loop shaped like `core_list_reverse`. Every row with J is
6195 instructions and 8 dispatches more on `ed25519_verify`, which is J's small cost again.
`blake3_hash_chunk` is 14,583 dispatches in every row.

The benchmarks cannot separate any of this. Three rows built from the same guest code timed
`blake3_hash_chunk` at 14.70, 14.52 and 15.46 µs, and three others sharing code spread from 14.06 to
16.35 µs, so every timing difference in that run is noise and the dispatch counts are the result.

So, beyond fusion and jump cost, which upstream already has, `generic-interpreter-rv64` contributes
one loop-unrolling heuristic that wins on one CoreMark loop and does nothing on the contracts. The
BLAKE3 improvement quoted earlier on this page is not reproduced by the interpreter tuning now that
the target specification carries the fusion features; the likeliest explanation is that those
features were the difference when it was measured against a specification without them.

### Which fusion features the contracts need

The target specification had all nineteen fusion features, on the grounds that each keeps a pair the
interpreter can fuse together. Left out one at a time, on the pinned toolchain, counted in
dispatches (exact here, since neither contract method prints anything that depends on time):

| without | static | `blake3_hash_chunk` | fused | `ed25519_verify` | fused |
|---|---|---|---|---|---|
| nothing (all nineteen on) | 6193 | 14,583 | 14,086 | 654,763 | 646,244 |
| all nineteen (none on) | 6231 | 14,647 | 14,134 | 654,828 | 652,562 |
| `fusion-logic-reg-reg` | 6196 | same | same | 654,766 | **652,374** |
| `fusion-lui-addi` | 6229 | **14,647** | **14,134** | 654,827 | 646,313 |
| `fusion-shxadd-load` | 6193 | same | same | same | 646,308 |
| `conditional-cmv-fusion` | 6191 | same | same | 654,761 | 646,292 |
| `fusion-auipc-addi`, `fusion-bfext` | 6193 | same | same | same | 646,245 |
| `fusion-auipc-load` | 6190 | same | same | 654,758 | 646,246 |
| any of the other twelve | 6193 | same | same | same | same |

`fusion-logic-reg-reg` is nearly all of it, and `fusion-lui-addi` is the only one BLAKE3 notices.
Twelve change nothing in either contract. `fusion-auipc-load` trades 2 fused dispatches for 5
unfused ones and three instructions, so it is not worth asking for.

The specification now carries the six that help and nothing else: `conditional-cmv-fusion`,
`fusion-auipc-addi`, `fusion-bfext`, `fusion-logic-reg-reg`, `fusion-lui-addi` and
`fusion-shxadd-load`. With exactly those six the counts are 6190 instructions, 14,583 / 14,086 and
654,758 / 646,246, which is all nineteen minus the `fusion-auipc-load` trade, so nothing else
matters even in combination.

### The one piece LLVM does not have: `unroll-shift-chains`

Shift-chain unrolling is the only part of `generic-interpreter-rv64` that helps and that nothing
upstream can switch on. It is on its own branch now,
[`claude/riscv-unroll-shift-chains`](https://github.com/nazar-pc/llvm-project/tree/claude/riscv-unroll-shift-chains),
as a tune feature rather than a CPU, so a target specification can ask for it. With the feature
on `generic-rv64` and the fusion features, CoreMark compiles to the same code as the ablation's C
row, byte for byte: 5064 instructions, 249,452,261 dispatches and 230,783,913 fused. It is not in
the target specification, because neither contract has a loop it applies to and the pinned
toolchain does not know it.

## 5.7 Reproducing it

Scripts in `interpreter-codegen/`, each meant to be run in an empty directory. All are resumable,
so re-running after a failure only repeats what did not finish.

### CoreMark

```bash
mkdir /tmp/interp && cd /tmp/interp
<repo>/specs/discussions/interpreter-codegen/measure-coremark.sh
```

It fetches the patched LLVM and builds `opt` and `llc` from it, fetches `riscv64-unknown-elf` GCC
14.2 and binutils 2.43.1 from questing, fetches this repository, and prints one row per
configuration: dispatches, dispatches with the interpreter's pair fusion, static instructions,
fusable pairs, and the interpreted score with the interpreter's pair fusion off and then on. About
an hour on four cores, nearly all of it LLVM. Sweep more configurations by setting `CONFIGS` to
lines of `name cpu -mattr extra-flags`, and note that
each one needs a distinct name or the CoreMark build script silently reuses the ELF. Both clones are
re-fetched on every run, so re-running after a branch moves measures the branch rather than what was
cloned the first time, and `ninja` runs unconditionally for the same reason.

The wrapper it generates leaves `clang` as a frontend only — `-Xclang -disable-llvm-passes` — so
both the mid-level pipeline and codegen come from the LLVM under test. That is the whole point;
§5.5 is what happens when only `llc` is replaced.

### Rust, for the contract workloads

The contracts are built by rustc, which carries its own LLVM fork, so `generic-interpreter-rv64`
cannot be selected until that fork is patched too.

```bash
mkdir /tmp/rustc-interp && cd /tmp/rustc-interp
<repo>/specs/discussions/interpreter-codegen/build-patched-rustc.sh
```

It resolves the commit behind the pinned nightly, checks out `rust-lang/rust` there, applies the
LLVM change to `src/llvm-project`, builds a stage-2 rustc with `download-ci-llvm` off — leaving it
on would silently fetch a prebuilt LLVM and ignore the patch — and reports `dispatch_count` on
`generic-rv64` and then on `generic-interpreter-rv64`. Several hours and about 40 GB of disk; it
builds LLVM and then rustc twice.

Afterwards, two environment variables pick the guest compiler and CPU for any Cargo command in this
checkout, leaving the host on the pinned toolchain and the repository unmodified:

```bash
AB_GUEST_TOOLCHAIN=/tmp/rustc-interp/rust/build/host/stage2/bin/rustc \
AB_GUEST_CPU=generic-interpreter-rv64 \
  cargo run --release -p ab-riscv-benchmarks --example dispatch_count
```

The checked-in CPU stays `generic-rv64` deliberately: an unrecognized CPU name is ignored with a
warning and leaves the subtarget with no scheduling model at all, which §4 measures as the worst
configuration of the lot — and on an RV64 target a stock LLVM then fails outright with
`RV64 target requires an RV64 CPU`, which is what selecting the new CPU on an unpatched toolchain
looks like.

### libriscv

```bash
mkdir /tmp/interp && cd /tmp/interp
<repo>/specs/discussions/interpreter-codegen/bench-libriscv.sh
```

Run in the same directory as `measure-coremark.sh` it reuses that run's LLVM build and GCC;
otherwise it builds them. It additionally fetches picolibc, CoreMark and libriscv, builds the guest
twice, and prints instructions dispatched, `.text` size and the wall-clock runs for each CPU.

Two things had to be adjusted to make the guest loadable, and both are the harness's problem rather
than the compiler's. picolibc's linker script packs `.text` and `.rodata` into one page; libriscv
maps each segment with its own permissions and rejects a page that is both, with a protection fault
raised before the program starts, so the script inserts one `ALIGN(4096)`. And CoreMark's POSIX
port takes its iteration count from `argv`, which a freestanding entry point does not supply, so
`SEED_METHOD=SEED_VOLATILE` pins it instead — otherwise CoreMark auto-calibrates against the guest
cycle counter and settles on a 15 ms run.

### Two traps in switching the guest toolchain

Both cost a full build to discover and neither announces itself, so they are worth naming.

**`RUSTUP_TOOLCHAIN` does nothing here.** Cargo passes build scripts `RUSTC` as an absolute path
into the host toolchain rather than as the `rustup` shim, and the nested Cargo honors that variable,
so the override is inherited straight past and the guest is built by the host compiler. The symptom
is a byte-identical guest ELF, or a `rustc` command line in an error naming the host toolchain. The
stage-2 sysroot also has no `cargo` of its own, so the shim falls back to the host's regardless.
`AB_GUEST_TOOLCHAIN` therefore clears `RUSTC`, `RUSTDOC`, `RUSTC_WRAPPER` and `LD_LIBRARY_PATH`, and
takes an absolute path as the compiler itself.

`AB_GUEST_FEATURES` is the third knob, a comma separated list appended to the specification's own so
that a later entry overrides an earlier one: `-interpreter-target` subtracts the tuning while the
CPU keeps its scheduling model, `+interpreter-target` adds the tuning to a CPU that has none. It
reaches LLVM through the target specification rather than through `-C target-feature`, so rustc's
own notion of which target features exist does not get a say.

**Editing the generated target specification does nothing either.** `TargetSpecification::create`
rewrites the JSON on disk from the copy compiled into `ab-contracts-tooling`, so an edit to the file
under `OUT_DIR` or the cache directory is overwritten on the next build. `AB_GUEST_CPU` substitutes
into the embedded copy instead.

## 6. Traps

- **Unrecognized target features are ignored with a warning build systems swallow.** Check with
  `rustc -Zunstable-options --print target-features --target <spec>.json`, and **run it from the
  repository root** so `rust-toolchain.toml` applies. From anywhere else a different toolchain
  answers and reports a different, older feature set — including the older `<name>-fusion` spelling,
  which makes a correct feature list look wrong. This cost a full round of measurements.
- **Wall clock cannot resolve a few percent from independent runs.** Three runs of the same
  binaries, fused versus unfused: hashing −2.9%, +1.2%, −4.6%; verify −6.6%, −7.3%, +0.6%. The signs
  disagree. Count instead — or, where only wall clock can answer, alternate the two builds and take
  per-round differences: §5.6 resolves 1.9% that way where the per-run spread is 3%.
- **Dispatch count is not the whole cost either.** §4 has a case where 10% fewer dispatches ran 3.4%
  slower.
- **Static instruction count is close to useless as a proxy.** `generic-interpreter-rv64` emits 2.5×
  the code of `generic-rv64` and executes 14.9% fewer instructions.
- **A toolchain is not a version, it is a set of binaries.** §5.5: a wrapper that ran clang's
  frontend and a newer `llc` was reported under the `llc`'s version while every mid-level decision
  in it came from the system clang, and the conclusion it supported was backwards. Name the binary
  that made the decision.
- **Build scripts cache on the environment variables they declare.** The CoreMark build script reruns
  on `RISCV_CC` and `COREMARK_ITERATIONS`; sweeping anything else (a `-mcpu` inside a wrapper, say)
  needs a distinct wrapper path per configuration or the ELF is silently reused. The same applies to
  the contract build: `AB_EXTRA_RUSTFLAGS` exists so that compiler flags can be swept at all, and
  `ab-riscv-benchmarks`' build script declares it for that reason.
